# WeKnora 租户管理与数据隔离分析

> 对 WeKnora 多租户架构的深入分析，包括数据隔离机制、二级用户支持、跨租户协作与权限模型。

## 一、租户模型概述

### 1.1 核心概念

WeKnora 的租户体系是**自动创建、一人一租户**的模式：

```
用户注册 → 自动创建 Tenant → 用户绑定 TenantID
```

并非传统 SaaS 的"先有企业租户再添加用户"的模式，而是每个用户注册时自动成为其工作区的拥有者。

### 1.2 数据模型

```go
// internal/types/tenant.go
type Tenant struct {
    ID               uint64              // 租户 ID（自增）
    Name             string              // 工作区名称（默认："用户名's Workspace"）
    APIKey           string              // API 访问密钥（AES-GCM 加密存储）
    Status           string              // 状态（active/inactive）
    RetrieverEngines  []RetrieverEngine  // 检索引擎配置（PostgreSQL/ES/Qdrant...）
    StorageEngineConfig *StorageConfig   // 存储引擎配置（S3/OSS/MinIO...）
    StorageQuota     int64               // 存储配额（默认：10737418240 = 10GB）
    AgentConfig      *AgentConfig        // Agent 默认配置
    ContextConfig    *ContextConfig      // 上下文处理配置
    WebSearchConfig  *WebSearchConfig    // 网络搜索配置
    ConversationConfig *ConversationConfig // 对话配置
    ParserEngineConfig *ParserEngineConfig // 文档解析引擎配置
    // ... 更多配置
}

// internal/types/user.go
type User struct {
    ID                   string    // UUID
    Username             string
    Email                string
    TenantID             uint64    // 所属租户 ID（外键）
    CanAccessAllTenants  bool      // 是否可跨租户访问
    IsActive             bool      // 是否激活
    // ... 更多字段
}
```

## 二、租户自动创建流程

### 2.1 注册流程

代码位置：`internal/application/service/user.go`

```
POST /api/v1/auth/register
    │
    ▼
1. 检查 DISABLE_REGISTRATION 配置
    │ → 若禁用，拒绝请求
    ▼
2. 创建 Tenant 记录
    tenant := &types.Tenant{
        Name:        fmt.Sprintf("%s's Workspace", username),
        Description: "Default workspace",
        Status:      "active",
        // ... 默认配置
    }
    │
    ▼
3. 创建 User 记录
    user := &types.User{
        Username: username,
        Email:    email,
        TenantID: createdTenant.ID,  // ← 绑定关系
        // ...
    }
    │
    ▼
4. 返回 JWT Token
```

### 2.2 关键发现

- **第一个注册的用户 == 系统超级管理员？** 不完全是。系统没有预设的"超级管理员"概念，但有 `CanAccessAllTenants` 字段控制跨租户访问。
- 可通过数据库手动设置 `can_access_all_tenants = true` 赋予用户跨租户访问权限。
- 通过配置 `tenant.enable_cross_tenant_access: true` 启用跨租户访问功能。

## 三、数据隔离机制

### 3.1 数据库层隔离

**所有核心数据表都包含 `tenant_id` 字段**，实现行级数据隔离：

| 表/模型 | 隔离方式 |
|---------|---------|
| **Knowledge**（知识） | `tenant_id` 字段 |
| **KnowledgeBase**（知识库） | `tenant_id` 字段 |
| **Chunk**（文档块） | `tenant_id` 字段 |
| **Session**（会话） | `tenant_id` 字段 |
| **Message**（消息） | `tenant_id` 字段 |
| **Model**（模型配置） | `tenant_id` 字段 |
| **Agent**（智能体） | `tenant_id` 字段 |

查询时，所有数据库操作都会携带 `tenant_id` 作为过滤条件：

```go
// 典型的数据库查询（repository 层）
func (r *knowledgeRepository) GetKnowledgeByID(ctx context.Context, tenantID uint64, id string) (*types.Knowledge, error) {
    var knowledge types.Knowledge
    err := r.db.WithContext(ctx).
        Where("tenant_id = ? AND id = ?", tenantID, id).  // ← 租户过滤
        First(&knowledge).Error
    return &knowledge, err
}
```

### 3.2 API 层隔离

认证中间件（`internal/middleware/auth.go`）确保了租户上下文的安全注入：

```
HTTP 请求
    │
    ▼
Auth 中间件
    ├── JWT Token 认证
    │   ├── 解析 Token → 获取 User
    │   ├── 读取 X-Tenant-ID Header（可选，跨租户切换）
    │   │   ├── 校验用户跨租户访问权限
    │   │   └── 验证目标租户存在
    │   └── 写入 Context：tenantID, tenant, user, userID
    │
    └── X-API-Key 认证（SDK 模式）
        ├── 从 API Key 提取 TenantID（AES-GCM 解密）
        ├── 验证 API Key 有效性
        └── 构造系统虚拟用户并写入 Context
```

Context 中的键值：
```go
types.TenantIDContextKey.String()   // → 当前操作的租户 ID
types.TenantInfoContextKey.String() // → 租户完整信息
types.UserContextKey.String()       // → 当前用户信息
types.UserIDContextKey.String()     // → 当前用户 ID
```

### 3.3 存储层隔离

对象存储（S3/OSS/MinIO）按租户划分目录/桶：

```go
// internal/application/service/tenant.go
// 每个租户可以有独立的存储桶配置
// 创建租户时检查桶名称全局唯一性
func (s *tenantService) checkBucketNameCollision(...) {
    // 检查所有租户的桶名称是否有冲突
    for tenantID, providers := range allBuckets {
        for provider, bucketName := range providers {
            if b != oldB && usedByOthers[provider] != nil && usedByOthers[provider][b] {
                return werrors.NewBadRequestError("存储桶名称已被其他租户使用")
            }
        }
    }
}
```

### 3.4 API Key 加密

租户 API Key 使用 **AES-256-GCM** 加密存储：

```go
// 生成：AES-GCM 加密(tenantID) → base64 → "sk-" + 前缀
// 验证时：截取 "sk-" → base64 解码 → AES-GCM 解密 → 提取 tenantID
```

- **TENANT_AES_KEY** 必须为 **32 字节**（AES-256 密钥）
- 生成命令：`openssl rand -hex 16`

## 四、跨租户访问机制

### 4.1 配置开关

```yaml
# config/config.yaml
tenant:
  enable_cross_tenant_access: false  # 默认关闭
```

### 4.2 跨租户访问流程

```
API 请求带 X-Tenant-ID Header
    │
    ▼
Auth 中间件检查：
1. cfg.Tenant.EnableCrossTenantAccess == true ?
2. user.CanAccessAllTenants == true ?
3. 目标租户存在？
    │
    ├── 全部通过 → 注入目标租户上下文
    └── 任一失败 → 403 Forbidden
```

### 4.3 跨租户搜索范围

知识搜索时，可通过 `KnowledgeSearchScope` 指定多个（租户, 知识库）组合：

```go
type KnowledgeSearchScope struct {
    TenantID uint64
    KBID     string
}
```

这允许有权限的用户同时搜索多个租户的知识库。

## 五、组织（Organization）协作系统

### 5.1 概述

**Organizations 是 WeKnora 实现跨租户协作的核心机制**，它独立于租户体系之上：

```
         Organization（组织/空间）
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
 成员 A      成员 B      成员 C
(TenantID=1) (TenantID=2) (TenantID=3)
    │           │           │
    └───────────┼───────────┘
        共享知识库 / 共享智能体
```

### 5.2 组织数据结构

```go
type Organization struct {
    ID                     string     // UUID
    Name                   string     // 组织名称
    OwnerID                string     // 所有者 UserID
    InviteCode             string     // 邀请码（8 字节随机 hex）
    InviteCodeExpiresAt    *time.Time // 邀请码过期时间
    InviteCodeValidityDays int        // 邀请码有效期（0/1/7/30 天，0=永久）
    RequireApproval        bool       // 加入是否需要审核
    Searchable             bool       // 是否可被搜索发现
    MemberLimit            int        // 成员上限（0=无限制，默认 200）
}

type OrganizationMember struct {
    ID             string        // UUID
    OrganizationID string        // 所属组织
    UserID         string        // 用户 ID
    TenantID       uint64        // 用户所属租户（关键：保留来源租户）
    Role           OrgMemberRole // admin / editor / viewer
}
```

### 5.3 角色权限体系

```go
const (
    OrgRoleAdmin  OrgMemberRole = "admin"   // 管理员（完全控制）
    OrgRoleEditor OrgMemberRole = "editor"  // 编辑者（可编辑内容但不可管理设置）
    OrgRoleViewer OrgMemberRole = "viewer"  // 查看者（仅查看和搜索）
)

// 权限等级
var roleLevel = map[OrgMemberRole]int{
    OrgRoleAdmin:  3,
    OrgRoleEditor: 2,
    OrgRoleViewer: 1,
}
```

### 5.4 知识库共享机制

```
Own Tenant (TenantID=1)             Organization
┌─────────────────┐               ┌─────────────┐
│   KnowledgeBase  │─── 共享 ───▶ │ Member A    │
│   (owned by U1)  │              │ (TenantID=2) │
└─────────────────┘               │ Member B    │
                                  │ (TenantID=3) │
                                  └─────────────┘
```

共享记录数据结构：
```go
type KnowledgeBaseShare struct {
    ID              string        // UUID
    KnowledgeBaseID string        // 被共享的知识库
    OrganizationID  string        // 目标组织
    SharedByUserID  string        // 分享者
    SourceTenantID  uint64        // KB 所属的源租户（关键：跨租户访问模型）
    Permission      OrgMemberRole // 分享权限级别
}
```

### 5.5 智能体（Agent）共享

与知识库共享类似，Agent 也有独立的共享表 `agent_shares`，同样包含 `SourceTenantID` 用于跨租户访问。

### 5.6 加入组织的方式

| 方式 | 条件 | 说明 |
|------|------|------|
| **邀请码加入** | 知道邀请码 | 直接加入，默认 viewer 角色 |
| **搜索加入** | 组织开启了 Searchable | 搜索发现后直接加入或申请 |
| **审核加入** | 组织开启了 RequireApproval | 提交申请 → 管理员审核 |
| **管理员添加** | 管理员有目标用户 ID | 直接添加成员 |

### 5.7 角色升级机制

```
普通成员 → 提交升级申请 → 管理员审核 → 升级角色
```

- 申请类型：`JoinRequestTypeUpgrade`
- 只能向更高权限升级
- 已经是 admin 不可再次申请

## 六、企业级多用户方案分析

### 6.1 当前架构的"一人一租户"模式

WeKnora 当前的设计是 **每个注册用户自动创建一个 Tenant**：

```
用户 A (TenantID=1) → 知识库 A1, A2, ...
用户 B (TenantID=2) → 知识库 B1, B2, ...
```

**优点**：
- 天然数据隔离，无需额外逻辑
- 每个用户自主管理自己的知识库
- 配置独立（模型、存储、检索参数）

**局限**：
- 不支持同一 Tenant 下多个用户共享知识库
- 不支持子账户/角色分级管理
- 企业场景需要额外的组织层来实现协作

### 6.2 当前的企业协作方案：Organization

对于 "一个租户多个二级用户" 的需求，当前架构通过 **Organization（组织/空间）** 来实现：

```
企业 "TechCorp" 的知识协作：
┌──────────────────────────────────────────────────┐
│              Organization: "TechCorp 知识库"       │
│  Owner: 用户 A (TenantID=1)                       │
│                                                    │
│  Members:                                          │
│  ├── 用户 A (admin)   ← TenantID=1 的知识库被共享   │
│  ├── 用户 B (editor)  ← TenantID=2 参与编辑         │
│  └── 用户 C (viewer)  ← TenantID=3 只读访问         │
│                                                    │
│  Shared KBs:                                       │
│  ├── KB-A-1 (来自 TenantID=1, 权限: admin)          │
│  ├── KB-B-1 (来自 TenantID=2, 权限: editor)         │
│  └── KB-A-2 (来自 TenantID=1, 权限: viewer)         │
└──────────────────────────────────────────────────┘
```

### 6.3 共享知识库的有效权限计算

用户对共享知识库的**有效权限** = min(分享权限, 用户在组织中的角色)：

```go
// organization.go
type KnowledgeBaseShareResponse struct {
    Permission   string `json:"permission"`      // 分享给组织的权限（viewer/editor/admin）
    MyRoleInOrg  string `json:"my_role_in_org"`  // 我在组织中的角色
    MyPermission string `json:"my_permission"`   // 有效权限 = min(Permission, MyRoleInOrg)
}
```

示例：
- 知识库被以 `editor` 权限共享给组织
- 成员 C 在组织中角色是 `viewer`
- 成员 C 对该 KB 的有效权限 = `viewer`

### 6.4 二级用户数据权限矩阵

| 操作 | Admin | Editor | Viewer |
|------|-------|--------|--------|
| 查看共享知识库 | ✅ | ✅ | ✅ |
| 搜索共享知识库 | ✅ | ✅ | ✅ |
| 对话问答（基于共享 KB） | ✅ | ✅ | ✅ |
| 添加/编辑知识 | ✅ | ✅ | ❌ |
| 删除知识 | ✅ | ❌ | ❌ |
| 修改知识库设置 | ✅ | ❌ | ❌ |
| 分享给其他组织 | ✅ | ❌ | ❌ |
| 管理组织成员 | ✅ | ❌ | ❌ |
| 删除组织 | ✅ (Owner) | ❌ | ❌ |

### 6.5 实现"同一个 Tenant 下多个二级用户"的建议

如果需要实现**标准 SaaS 多租户**模式（一个企业租户 → 多个子用户），可参考以下扩展方案：

#### 方案 A：在现有架构上扩展

1. **新增 TenantUser 表**：
```sql
CREATE TABLE tenant_users (
    tenant_id   BIGINT,
    user_id     VARCHAR(36),
    role        VARCHAR(32),  -- owner / admin / member / viewer
    PRIMARY KEY (tenant_id, user_id)
);
```

2. **修改注册逻辑**：支持通过邀请链接注册到已有 Tenant

3. **权限控制**：在 Auth 中间件注入 TenantUser 角色，handler 层按角色鉴权

#### 方案 B：利用现有 Organization 扩展

Organization 已有完善的成员管理和权限控制，可以通过以下方式扩展：
- 允许将 Organization 设置为"主工作区"模式
- 支持 Organization 级别的资源归属（而非个人 Tenant）
- 打通 Organization → Tenant 的资源访问权限

#### 方案 C：纯 Organization 模式的"虚拟企业空间"

将 Organization 直接作为企业空间使用：
- 企业管理员创建 Organization
- 员工通过邀请加入 Organization
- 所有知识库创建时归属于 Organization 而非个人 Tenant
- 需修改知识库的归属模型，从 `tenant_id` → `organization_id` 或双归属

## 七、认证与安全

### 7.1 认证方式

| 方式 | 说明 |
|------|------|
| **JWT Token** | 登录获取，含过期时间，支持 Refresh |
| **X-API-Key** | 租户级别的 API 密钥，用于 SDK/API 调用 |
| **OIDC** | OpenID Connect 单点登录（企业集成） |

### 7.2 安全关键点

- **TENANT_AES_KEY**：32 字节，用于 API Key 加密，泄露导致所有 API Key 可被解密
- **JWT_SECRET**：建议使用 `openssl rand -base64 32` 生成
- **DB_PASSWORD**：`.env` 中特殊字符需用单引号包裹
- **DISABLE_REGISTRATION**：生产环境建议注册后关闭，防止未授权注册

### 7.3 上下文安全

租户上下文仅通过 Auth 中间件注入，**不可通过请求参数直接指定租户**（防止租户越权）：

```go
// ❌ 不能通过 URL 参数指定租户
GET /api/v1/knowledge?tenant_id=2

// ✅ 只能通过认证 Token 或 X-Tenant-ID Header（需权限检查）
GET /api/v1/knowledge
Authorization: Bearer <token>
X-Tenant-ID: 2  // 仅在 enable_cross_tenant_access 且用户有权限时有效
```

## 八、总结与建议

### 8.1 当前架构适用场景

| 场景 | 适用度 | 说明 |
|------|--------|------|
| **个人知识管理** | ✅ 完美 | 一人一租户，数据完全隔离 |
| **小团队协作** | ✅ 良好 | 通过 Organization 共享 KB |
| **企业知识库** | ⚠️ 需扩展 | 需要 Tenant 多用户支持 |
| **多租户 SaaS** | ⚠️ 需扩展 | 需企业级租户层级 |
| **API/SDK 集成** | ✅ 良好 | X-API-Key 支持 |

### 8.2 二次开发重点

1. **Tenant 多用户**：实现一个 Tenant 下有多个 User，是目前最需要的企业级功能
2. **数据权限分级**：KB 级、Tag 级、Document 级的细粒度权限
3. **配额管理**：已有 StorageQuota 字段，但未完全实现配额限制逻辑
4. **审计日志**：跨租户操作的审计追踪
5. **SSO 集成**：企业统一认证（OIDC 已有基础）
