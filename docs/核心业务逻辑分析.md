# WeKnora 核心业务逻辑分析

> 从文档上传 → 处理 → 入库 → 搜索 → 问答的完整链路分析

## 一、全链路概览

```
用户上传文档
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 1. 接收层 (Handler)                                    │
│    文件上传 / URL 提交 / 手动录入 / 数据源导入            │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 2. 存储层 (FileService)                                │
│    文件存储到对象存储（S3/OSS/MinIO/Local）              │
│    → 生成 FilePath                                    │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 3. 异步任务 (Asynq)                                     │
│    将文档处理任务推入 Redis 队列                         │
│    → 返回任务状态 "pending"                             │
└──────────────────┬───────────────────────────────────┘
                   │ (异步执行)
                   ▼
┌──────────────────────────────────────────────────────┐
│ 4. 文档解析 (DocReader gRPC)                            │
│    Go → gRPC → Python docreader 服务                  │
│    文件格式解析 → Markdown 文本 → 图片处理                │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 5. 文本分块 (Chunker)                                   │
│    Markdown 级联分割（保护各 Block 完整性）              │
│    → 父子分块策略（Parent-Child Chunking）              │
│    → 生成图文混排的 Chunk 列表                          │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 6. 向量嵌入 (Embedding)                                 │
│    调用 LLM Embedding 模型生成向量                      │
│    → 索引内容 = Chunk.Content（或问题+答案）              │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 7. 多路索引 (Indexing)                                  │
│    向量索引 → pgvector HNSW                             │
│    关键词索引 → pg_search BM25                         │
│    知识图谱索引 → Neo4j（可选）                          │
│    → 更新状态 "completed"                              │
└──────────────────┬───────────────────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────────────────┐
│ 8. 用户搜索问答                                         │
│    Query → 意图识别 → 查询重写 → 并行搜索               │
│    → 重排序 → 合并去重 → 构建Prompt → LLM生成           │
└──────────────────────────────────────────────────────┘
```

## 二、文档上传方式

系统支持多种知识入口（定义于 `internal/types/knowledge.go`）：

| 方式 | 渠道常量 | 说明 |
|------|---------|------|
| **Web UI 上传** | `ChannelWeb` | 拖拽/选择文件上传 |
| **API 接口** | `ChannelAPI` | 通过 REST API 提交 |
| **URL 导入** | `ChannelWeb` | 输入网页 URL 自动抓取 |
| **手动录入** | `ChannelWeb` | Markdown 编辑器直接写 |
| **浏览器插件** | `ChannelBrowserExtension` | 浏览器扩展保存 |
| **IM 集成** | `ChannelWechat/Wecom/Feishu/Dingtalk/Slack` | 即时通讯机器人 |
| **Notion** | `ChannelNotion` | 数据源导入 |
| **语雀** | `ChannelYuque` | 数据源导入 |
| **FAQ 批量导入** | `ChannelWeb/API` | Excel/CSV 批量上传 |

### 文件上传流程（关键代码路径）

```
handler/knowledge.go → knowledgeService.CreateKnowledgeFromFile()
  ├── 校验文件类型（通过扩展名白名单）
  ├── 去重检查（MD5 哈希）
  ├── 上传到对象存储（fileSvc.UploadFile）
  ├── 创建 Knowledge 记录（状态："pending"）
  └── 推入 Asynq 异步任务（Type: TaskProcessKnowledge）
```

## 三、文档解析（DocReader 服务）

### 3.1 通信机制

Go 后端通过 gRPC 调用 Python DocReader 服务：

```go
// docreader/client/client.go
conn, _ := grpc.Dial("dns:///"+addr, ...)
DocReaderClient: proto.NewDocReaderClient(conn)

// 调用示例（在 knowledge.go 中）
resp, err := s.documentReader.Read(ctx, &proto.ReadRequest{
    FilePath:  knowledge.FilePath,
    FileType:  fileType,
    // Parser engine overrides (e.g. MinerU endpoint)
    Engine:    overrides,
})
```

### 3.2 Python 解析器架构（`docreader/parser/`）

```
parser/
├── registry.py        # 解析器注册表，根据文件扩展名路由
├── base_parser.py     # 解析器基类
├── chain_parser.py    # 责任链模式组合解析器
├── doc_parser.py      # DOC 文档解析
├── docx_parser.py     # DOCX 解析（最复杂，支持图表）
├── pdf_parser.py      # PDF 解析
├── excel_parser.py    # Excel 解析
├── markdown_parser.py # Markdown 解析
├── markitdown_parser.py # 通用转换（使用 markitdown 库）
├── image_parser.py    # 图片解析
├── web_parser.py      # 网页解析
└── storage.py         # 图片/附件转储到对象存储
```

解析器的注册与路由：
```python

    registry = {
        "pdf": PDFParser,

        "xlsx": ExcelParser,
        "pptx": MarkitdownParser,

        "html": WebParser,
        "jpg": ImageParser,
        # ... 更多映射
    }
```

### 3.3 图片处理

文档中的图片会被：
1. 提取并上传到对象存储
2. 通过 VLM 模型生成图片描述（caption）
3. 通过 OCR 模型提取文字（OCR text）
4. 在文本中保留图片位置引用

图片信息结构：
```go
type ImageInfo struct {
    URL         string // COS 对象存储 URL
    OriginalURL string // 原始 URL
    StartPos    int    // 文本中的起始位置
    EndPos      int    // 文本中的结束位置
    Caption     string // VLM 生成的图片描述
    OCRText     string // OCR 识别的文字
}
```

## 四、文本分块（Chunking）

### 4.1 分块配置

```yaml
# config/config.yaml
knowledge_base:
  chunk_size: 512        # 每个 chunk 的最大字符数
  chunk_overlap: 50      # chunk 之间的重叠字符数
  split_markers:          # 分割符（按优先级排列）
    - "\n\n"             # 段落分隔
    - "\n"               # 换行分隔
    - "。"               # 句号分隔
```

### 4.2 分块策略：Markdown 级联分割

分块器（`internal/infrastructure/chunker/`）采用 **Markdown-aware 级联分割**策略：

1. **保护 Markdown Block 完整性**：Table/Code 块不会被切割
2. **按分隔符逐级降级**：`\n\n` → `\n` → `。` → 字符级截断
3. **父-子块策略**（Parent-Child Chunking）：
   - **父块**（Parent）：更大的上下文窗口（如 2048 字符）
   - **子块**（Child）：精细粒度的检索单元（如 512 字符）
   - 检索时命中子块 → 返回关联的父块内容（召回更完整上下文）

### 4.3 Chunk 类型体系

```go
const (
    ChunkTypeText           = "text"            // 普通文本
    ChunkTypeParentText     = "parent_text"     // 父级文本（仅供上下文）
    ChunkTypeImageOCR       = "image_ocr"       // 图片 OCR 文本
    ChunkTypeImageCaption   = "image_caption"   // 图片描述
    ChunkTypeSummary        = "summary"         // 摘要
    ChunkTypeEntity         = "entity"          // 知识图谱实体
    ChunkTypeRelationship   = "relationship"    // 知识图谱关系
    ChunkTypeFAQ            = "faq"             // FAQ 条目
    ChunkTypeWebSearch      = "web_search"      // 网页搜索结果
    ChunkTypeTableSummary   = "table_summary"   // 数据表摘要
    ChunkTypeTableColumn    = "table_column"    // 数据表列描述
    ChunkTypeWikiPage       = "wiki_page"       // Wiki 页面同步
)
```

### 4.4 Chunk 数据模型

```go
type Chunk struct {
    ID              string    // UUID
    SeqID           int64     // 自增整数 ID（对外暴露）
    TenantID        uint64    // 租户隔离
    KnowledgeID     string    // 所属知识
    KnowledgeBaseID string    // 所属知识库
    Content         string    // 实际文本内容
    ChunkIndex      int       // 在文档中的位置
    ChunkType       string    // 类型标识
    ParentChunkID   string    // 关联的父块（用于父子分块）
    PreChunkID      string    // 前一个 Chunk
    NextChunkID     string    // 后一个 Chunk
    ImageInfo       string    // 关联的图片信息（JSON）
    ContentHash     string    // 内容哈希（FAQ 去重用）
    // ... 更多字段
}
```

## 五、向量嵌入与索引

### 5.1 嵌入生成

每个需要索引的 Chunk 都会经过 Embedding 模型处理：

- 索引内容策略：
  - **普通文档**：`Chunk.Content`
  - **FAQ**：`标准问题 + 所有相似问题`（答案不参与向量化）
  - **图片**：`Caption + OCR Text`
- 使用 **半精度向量**（halfvec）存储以节省空间
- 批量嵌入（Batch Embedding）减少 API 调用次数

### 5.2 多路索引

```
                    Chunk 内容
                        │
          ┌─────────────┼─────────────┐
          ▼              ▼              ▼
    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │ 向量索引   │  │ 关键词索引│  │ 图谱索引  │
    │ pgvector  │  │pg_search │  │ Neo4j    │
    │ HNSW      │  │ BM25     │  │ (可选)   │
    └──────────┘  └──────────┘  └──────────┘
         │              │              │
         └──────────────┼──────────────┘
                        │
                  混合检索融合
```

- **向量检索**（Vector）：基于语义相似度，使用余弦距离
- **关键词检索**（Keywords）：基于 BM25 算法，精确匹配
- **图谱检索**（Graph）：基于实体关系网络（需 Neo4j）

### 5.3 索引状态机

```
pending → processing → completed
                ↓
              failed
```

状态定义：
- `pending`：等待异步处理
- `processing`：正在解析/嵌入/索引中
- `completed`：全部完成
- `failed`：处理失败（可查看 error_message）
- `deleting`：正在删除（防止异步任务冲突）

## 六、搜索与问答管道

### 6.1 管道架构

搜索问答采用 **插件化管道**（Plugin Pipeline）模式，定义于 `internal/application/service/chat_pipeline/`：

```go
// session_knowledge_qa.go 中管道组装
pipeline = types.NewPipelineBuilder().
    Add(types.LOAD_HISTORY).           // 1. 加载历史消息
    Add(types.QUERY_UNDERSTAND).       // 2. 查询意图识别
    Add(types.CHUNK_SEARCH_PARALLEL).  // 3. 并行搜索（向量+关键词+实体+Web）
    Add(types.CHUNK_RERANK).           // 4. 重排序
    AddIf(req.WebSearchEnabled, types.WEB_FETCH).  // 5. 网页内容获取（可选）
    Add(types.CHUNK_MERGE).            // 6. 合并去重 + FAQ 增强
    Add(types.FILTER_TOP_K).           // 7. 截取 Top-K
    Add(types.DATA_ANALYSIS).          // 8. 数据分析（可选）
    Add(types.INTO_CHAT_MESSAGE).      // 9. 组装 LLM Prompt
    Add(types.CHAT_COMPLETION_STREAM). // 10. 流式 LLM 回答
    Build()
```

### 6.2 各阶段详解

#### 阶段 1: LOAD_HISTORY（加载对话历史）
- 加载当前会话的最近 N 轮对话
- 提取历史中的 KnowledgeReferences

#### 阶段 2: QUERY_UNDERSTAND（查询理解）
- **查询重写**：将口语化/模糊的问题改写为精确的检索查询
- **意图识别**：判断用户意图（闲聊/知识问答/数据分析等）
- **查询扩展**：基于上下文生成扩展关键词

#### 阶段 3: CHUNK_SEARCH_PARALLEL（并行搜索）

核心实现在 `search.go` 中：

```
                    用户查询（已重写）
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ KB 搜索   │    │ Web 搜索  │    │ FAQ 搜索  │
    │(向量+B25) │    │(可配置)   │    │(精确匹配) │
    └────┬─────┘    └────┬─────┘    └────┬─────┘
         │               │               │
         └───────────────┼───────────────┘
                         ▼
                    合并结果集
```

搜索优化策略：
- **同模型复用嵌入**：相同 Embedding 模型的知识库共享向量计算
- **分组批量检索**：合并全 KB 搜索为一次检索调用
- **直接加载兜底**：小知识条目跳过检索直接加载全部 chunks
- **低召回扩展**：召回不足时触发查询扩展

#### 阶段 4: CHUNK_RERANK（重排序）

- 使用 Rerank 模型对检索结果重新打分
- 截取 rerank_top_k（默认 30）条
- 支持 Cross-encoder 重排序

#### 阶段 5: CHUNK_MERGE（合并去重）

核心实现在 `merge.go` 中：

1. **ID 去重**：相同 Chunk ID 只保留一个
2. **内容签名去重**：相同内容只保留最高分
3. **父块展开**：将子块的父块内容填充进来
4. **部分重叠去重**：内容高度重叠（≥85%）的低分结果丢弃
5. **FAQ 增强**：高置信度 FAQ 标记 `match="exact"` 直接回答

FAQ 优先级策略（`into_chat_message.go`）：
```
IF FAQPriorityEnabled AND has_faq_results THEN
    高置信度 FAQ → <source type="faq" priority="high"> (match="exact")
    普通 FAQ     → <source type="faq" priority="high">
    文档 Chunk   → <source type="document" priority="supplementary">
```

#### 阶段 6: INTO_CHAT_MESSAGE（组装 Prompt）

将搜索上下文和用户问题组装为 LLM 输入格式：

```xml
<documents>
  <document>
    <title>文档标题</title>
    <description>文档描述</description>
  </document>
</documents>

<source type="faq" priority="high">
  <context id="FAQ-1" match="exact">标准问题：XXX\n答案：YYY</context>
</source>

<source type="document" priority="supplementary">
  <context id="DOC-1">文档片段内容...</context>
</source>
```

Prompt 模板来自 `config/prompt_templates/context_template.yaml`，通过占位符替换：
- `{query}` → 用户问题
- `{contexts}` → 上面构建的上下文 XML
- `{language}` → 用户语言偏好

#### 阶段 7: CHAT_COMPLETION_STREAM（流式回答）

- 使用 Server-Sent Events (SSE) 推送
- 支持 "思考链"（Chain of Thought）流式展示
- 支持引用溯源（KnowledgeReferences 返回给前端）

## 七、FAQ 系统

### 7.1 FAQ 数据结构

```go
type FAQChunkMetadata struct {
    StandardQuestion  string         // 标准问题
    SimilarQuestions  []string       // 相似问题列表
    NegativeQuestions []string       // 反例问题（不匹配这些）
    Answers           []string       // 答案列表
    AnswerStrategy    AnswerStrategy // "all" 或 "random"
}
```

### 7.2 FAQ 索引策略

- **索引内容**：标准问题 + 所有相似问题（答案不索引）
- **匹配方式**：
  - 向量匹配：用户问题 vs 索引问题
  - 关键词匹配：BM25 文字匹配
  - 精确匹配：ContentHash 比对
- **反例过滤**：用户问题匹配到 NegativeQuestions 时过滤该条目

### 7.3 FAQ 批量导入

```
Excel/CSV → 解析验证 → 异步批量写入 → Chunk 创建 → Embedding → 索引
```

- 支持 Append（追加）和 Replace（替换）两种模式
- 异步处理，通过 Redis 存储进度
- 支持 DryRun 模式（仅验证不导入）
- 部分失败容忍机制（相似问过长被移除但条目仍可导入）

## 八、混合检索策略

### 8.1 HybridSearch 实现

```
输入查询
    │
    ├──→ 向量检索（pgvector cosine similarity）
    │     └── 返回 Top-K 结果
    │
    ├──→ 关键词检索（pg_search BM25）
    │     └── 返回 Top-K 结果
    │
    └──→ 结果融合
          └── RRF (Reciprocal Rank Fusion) 融合算法
```

### 8.2 检索配置

```yaml
conversation:
  embedding_top_k: 30       # 向量检索 Top-K
  vector_threshold: 0.2     # 向量相似度阈值
  keyword_threshold: 0.3    # 关键词阈值
  rerank_threshold: 0.3     # 重排序阈值
  rerank_top_k: 30          # 重排序后保留数
  enable_rewrite: true      # 启用查询重写
  enable_query_expansion: true  # 启用查询扩展
  enable_rerank: true       # 启用重排序
```

## 九、知识图谱（可选）

知识图谱通过 Neo4j 实现：
- **实体抽取**：从文档 Chunk 中自动识别实体
- **关系抽取**：识别实体之间的关系
- **图谱存储**：存入 Neo4j 图数据库
- **图谱检索**：检索时可通过关系网络扩展上下文

相关 Chunk 类型：
- `ChunkTypeEntity`：实体节点
- `ChunkTypeRelationship`：关系边

启用方式：在配置中设置 Neo4j 连接并启用知识图谱功能。

## 十、Agent 系统

Agent 系统（`internal/agent/`）提供更复杂的智能体能力：

```
用户输入 → Agent 引擎
    ├── 工具调用（Tool Calling）
    ├── 知识库选择（KB Selection）
    ├── Web 搜索决策
    ├── MCP 工具调用
    └── 多步推理
```

- 使用 **ReAct** 推理模式
- 支持自定义 Agent 预设（`config/builtin_agents.yaml`）
- Skills 系统可扩展能力
- 支持 MCP（Model Context Protocol）工具调用
